# App Review Notes — Build 20 Apple Remediation

## Build 29 live-site reliability remediation

Build 29 registers the previously linked courier, customer-onboarding, and fleet routes; returns client validation errors for malformed tracking codes; standardizes the dynamic Maps loader with the Directions library; uses the environment-specific Paystack public key; adds explicit courier earnings retry and error states; removes the duplicate explicit analytics script; and adds a branded PWA manifest with 192px and 512px icons.

## What changed after build 2.0.2 (13)

Mzansi Couriers now presents an app-branded account entry screen before authentication. On iPhone and iPad, the secure identity-provider flow is opened through the Capacitor in-app browser surface rather than assigning the login URL to the device’s default browser. After the server completes the existing OAuth exchange and creates the normal signed session, it returns through the registered `mzansi://auth/callback` app URL. The app closes the authentication surface and refreshes the real backend session. Build 20 also adds a native-only operational launch panel on the app entry route so the first native surface directs users to delivery work—booking, tracking, route work, proof capture, offline route state, and account security—rather than presenting only public marketing content. Build 21 adds local parcel search against the saved route snapshot, so a courier can find a specific tracking code, stop, address, city, status, or parcel detail without internet access. Build 22 refines the native visual hierarchy with translucent iOS-style headers, large titles, grouped cards, selected tab states, restrained shadows, and safe-area-aware 44-point controls across courier, customer, and account screens. Build 23 adds persistent high-contrast dark mode with a courier header toggle and an Account settings toggle for night-shift work. Build 24 adds the visible Home-screen Dark/Light button and an automatic 18:00–06:00 schedule based only on the device’s local clock. Build 25 adds the animated sun/moon transition, Build 26 adds optional brief tap feedback without adding feedback to automatic schedule changes, and Build 27 adds a contained visual ripple on direct theme taps with Reduce Motion support.

The web deployment retains its normal browser fallback. The backend continues to use the existing OAuth provider, database user synchronization, signed session cookie, and delivery APIs. Native requests are additionally recognized when they present the same signed session token as a bearer token; no production credentials are hardcoded into the app.

Build 16 adds an authenticated **Account settings** screen at `/settings/account`, reachable from the native courier and customer headers. Users can choose **Delete my account**, confirm by typing `DELETE MY ACCOUNT`, and complete deletion in the app without opening a browser. Personal profile data, saved addresses, preferences, notifications, payment methods, and courier profile data are removed; delivery custody, payment, tax, and dispute records are retained only in anonymized form where operationally required. Build 17 stores the native bearer session in the iOS Keychain and clears it on logout, unauthorized recovery, and account deletion. Build 18 adds a native LocalAuthentication check from Account settings so users can verify Face ID, Touch ID, or device passcode availability without leaving the app. Build 19 refines the iOS presentation with safe-area-aware screens, large-title hierarchy, grouped delivery surfaces, compact status controls, touch feedback, reduced-motion support, and a Home/Route/Account tab bar for the focused mobile experiences. Build 20 makes the native entry point explicitly operational and documents the concrete Guideline 4.2 reviewer path in `APP_REVIEW_GUIDELINE_4_2_RESPONSE.md`. Build 21 adds offline search over the saved courier route snapshot.

## Courier functionality available for review

The courier route is not a static demonstration. It uses persisted delivery-run state and real server procedures for parcel acceptance, route start, pickup/arrival actions, proof-of-delivery evidence, customer confirmation handoff, relay exceptions, and completion. The iOS package includes native-backed camera capture for delivery evidence, device location permission and route state, local route notifications, and visible offline/online feedback. The route displays the next parcel, its tracking code, payment readiness, route progress, and the required action for the current stop. It also offers a native MapKit destination view on iOS and a camera-photo QR/barcode decoder that compares the scanned value with the real next-stop tracking code. Build 18 stores the latest route snapshot locally, queues route-start and proof-photo actions while offline, and shows the pending-sync count. Build 19 gives the focused courier and customer mobile routes a more App Store-native visual hierarchy, safe-area spacing, grouped cards, large titles, and touch-friendly Home/Route/Account navigation rather than a desktop-scaled web layout. Build 20 exposes these utility paths from the native-only entry panel so the reviewer can reach the operational surfaces immediately.

## Review demonstration path

Use the review account supplied in App Store Connect review notes. Sign in from the in-app Mzansi account screen, choose the appropriate customer or courier role, and open the dashboard. For a courier account, keep location permission enabled, open the current route, start the route, review the next parcel and tracking code, use the location-aware route action, and capture delivery evidence with the in-app camera. The current route state and proof actions are persisted through the existing backend.

## Remaining validation

Build 19 must still be tested in Xcode on a physical iPhone and an iPad Air 11-inch-class simulator or device. The Mac-side validation must confirm the OAuth provider returns through the registered `mzansi://auth/callback` scheme, the authentication window dismisses, the session refreshes, the Account settings screen is reachable from both mobile roles, and account deletion signs the user out without crashing. Camera/location permission prompts should appear only when the courier action requires them. The existing Paystack payout-review and controlled-transfer checks are unrelated and remain paused.
